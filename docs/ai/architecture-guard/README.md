# Architecture Guard

Architecture Guard is a lightweight safety net for AI-generated changes in Anemoi_Open. It is not a replacement for code review, tests, or runtime verification. It catches common violations early so agents do not repeatedly introduce the same architecture and security problems.

## Purpose

The guard protects non-negotiable engineering rules from `AGENTS.md`, the AI Engineering Handbook, and the core AI guidance:

- controllers must stay thin;
- business behavior must go through CQRS/application handlers;
- production code must not introduce unapproved `Guid.NewGuid()` usage where generated IDs should use project conventions;
- AutoMapper must not be introduced where Mapperly is the project standard;
- role-name-based authorization must not replace permission-based authorization;
- frontend authorization must not use display roles instead of `user.permissions`.

## Components

### PowerShell Launcher

Path:

```text
scripts/architecture-guard.ps1
```

Responsibilities:

- scans C#, TypeScript, and TSX files with fast regex checks;
- excludes `bin`, `obj`, `.git`, and `node_modules`;
- detects common controller, authorization, GUID, AutoMapper, and frontend role-authorization violations;
- builds and runs the Roslyn guard project when available.

Example:

```powershell
pwsh ./scripts/architecture-guard.ps1
```

Scan a narrower path:

```powershell
pwsh ./scripts/architecture-guard.ps1 -Path ./Anemoi.Hr
```

Skip building the Roslyn project when it was already built:

```powershell
pwsh ./scripts/architecture-guard.ps1 -SkipBuild
```

### Roslyn Analyzer Console

Path:

```text
tools/Anemoi.ArchitectureGuard/
```

This is a Roslyn-based console analyzer, not a NuGet analyzer package. It parses C# syntax trees and reports architecture violations with rule IDs.

Run directly:

```powershell
dotnet run --project ./tools/Anemoi.ArchitectureGuard/Anemoi.ArchitectureGuard.csproj -- --path .
```

## Rule Set

| Rule | Area | Description |
| --- | --- | --- |
| `ANEMOI001` | Backend / API | Controller references `DbContext`. Controllers must delegate to CQRS handlers. |
| `ANEMOI002` | Backend / Domain/Data | Production code calls `Guid.NewGuid()`. Use project ID generation conventions where generated GUIDs are required. |
| `ANEMOI003` | Backend / Mapping | AutoMapper usage detected. Use Mapperly. |
| `ANEMOI004` | Backend / Security | Role-name-based `[Authorize(Roles = ...)]` detected. Use permission constants and `[HasPermission]`. |
| `ANEMOI005` | Frontend / Security | Frontend role-based authorization pattern detected. Use `user.permissions`. |
| `ANEMOI006` | Backend / API | Controller body appears too heavy, such as loops or transaction/persistence calls. Keep controllers thin. |

## Exit Codes

- `0`: guard completed without violations.
- `1`: guard found violations.
- `2`: invalid scan path or guard input.

## When To Run

Run Architecture Guard for:

- backend implementation;
- API/controller changes;
- permission/security changes;
- workflow changes;
- frontend permission visibility changes;
- bugfixes generated by AI agents;
- pre-review checks before claiming implementation readiness.

It can also be called from the default verification script:

```powershell
pwsh ./scripts/verify.ps1 -IncludeArchitectureGuard
```

## Reporting Rules

Architecture Guard output is execution evidence only for the rules it checks. Passing the guard does not prove the application works.

Use it in reports like this:

```text
Architecture Guard: PASS - scripts/architecture-guard.ps1 completed with exit code 0.
```

If the guard was not executed, report:

```text
Architecture Guard: N/A - not executed for documentation-only change.
```

Do not use Architecture Guard as a substitute for:

- `dotnet build Anemoi.sln`;
- relevant tests;
- API allowed/denied checks;
- database verification;
- browser validation;
- workflow history and target status checks;
- GitHub Actions status.

## Maintenance Rules

- Add a rule only when it protects a documented project standard.
- Prefer a low-false-positive rule over a broad noisy rule.
- If a violation is legitimate for tests, migrations, generated code, or infrastructure, narrow the rule or exclusion instead of ignoring all failures.
- Keep rule IDs stable once introduced.
- Document every new rule in this README.
